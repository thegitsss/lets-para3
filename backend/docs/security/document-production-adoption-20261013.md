# LPC production document-security adoption and rollback

Prepared 2026-10-13. **Design only. Production change, object inventory/migration, deployment and charges each require explicit authorization.** The staging template must never be applied to the production bucket. Current confirmed default: SSE-S3/AES256; user screenshots show existing active GuardDuty plan 12d0866a656f5bf59eb2 on paraconnect-uploads, us-east-1, account 096929701923.

## Gates before any adoption

1. Finish isolated staging verification: actual SSE-KMS uploads/decrypts, exact key policies, scanner tag writing, negative access tests, role/interface checks, failure/retry recovery, exports and version races. Freeze the exact application candidate and reviewed policies. Local tests alone cannot pass this gate.
2. Under separate read-only inventory authorization, enumerate production object **versions** and relevant application references without downloading document content. Record size, storage class, encryption algorithm/key ARN, version ID, ETag, content metadata, current managed scan tag, retention/lock status and consumer. Bucket defaults are not an object inventory. Include Matter and pre-engagement files, old versions, resumes, writing samples/certificates, profile images, previews, audio attachments, generated archives and receipts. Preserve a protected inventory outside public logs; no real data enters staging.
3. Read current bucket policy, CORS, lifecycle, versioning/ownership/public-block settings, protection-plan prefix coverage, scanner/runtime roles, backup/export identities and operational alerts. Confirm which controls are actually enforced. Identify all existing anonymous/direct S3 URLs before private KMS migration; KMS-encrypted objects do not support anonymous S3 delivery. Profile-photo delivery must use LPC's approved server path; authenticated documents require participant/account checks. Cache/CDN behavior and cross-origin signed upload headers need isolated verification.
4. Produce the exact production change set and migration budget using measured object count/bytes/versions. Obtain explicit production deployment approval. Create **one separate production CMK**, not reuse the staging key; retain it and its alias. Annual rotation is proposed, with $1 base plus first/second rotated-material charges described in the staging costing document. No duplicate production bucket or GuardDuty plan is proposed.

## Compatibility before writes change

Grant the existing production application and the existing GuardDuty scanner narrowly scoped GenerateDataKey/Decrypt access through regional S3 to the new production CMK. Include both bucket/object encryption contexts for Bucket Key compatibility. Keep administrative recovery separate from runtime permissions. Validate scanner access before requiring the new key on writes. Update the existing protection plan's role permissions/coverage only through an approved change; do not replace a working plan casually.

The compatible release must read both existing SSE-S3 files and new SSE-KMS files; S3 downloads need no upload encryption header. New writes and presigned PUTs specify the exact production CMK ARN. Test multipart uploads, server-generated documents, photo processing, pre-engagement uploads, previews, signed reads and exports. Presigned URLs signed by the application must retain authorization checks before issuance and S3 enforcement after issuance. Pin document version IDs where applicable and revalidate identity/scan after reads. Public photo approvals remain independent of a clean malware result.

Do not copy the staging identity-only bucket deny into production until every authorized scanner, backend, recovery/backup/export and administrative identity is reviewed. Do not quietly carry the legacy-unverified manifest into a claim that all production documents are scanned. Existing legacy exceptions must be inventoried and retired per verified file/version; any temporary compatibility allowance remains explicitly unverified and cannot apply to new writes. Deployment must not lock users out of their old files without a reviewed transition.

## Existing-file migration

Changing bucket default encryption affects future writes; it does **not** re-encrypt existing objects. Enable/confirm versioning under approval before rewriting. Use a bounded, checkpointed, server-side same-region copy of each reviewed current object to a new version encrypted with the exact CMK. Preserve Content-Type, Content-Disposition, user metadata and non-security tags; explicitly discard inherited clean-scan tags. A re-encrypted version must receive its own clean scan before application records refer to it or it becomes available through a controlled cutover. A reused ETag is not proof that scanning occurred. Guard against concurrent edits with source version IDs and conditional checks; record old/new version IDs and results in a protected migration ledger. Do not download copies through Render or send content into test accounts.

Until the new version is clean, maintain access to a previously authorized, clean older version through an explicit pinned reference if the transition design supports it. Otherwise pause that file's availability with an honest scanning status. Never inherit a clean result, forge tags, remove quarantine, or permit a pending new current version just to avoid interruption. Invalid/unsupported, failed and unavailable scans remain blocked pending operator review and bounded rescan. Repeated rescans are billable and must be tracked.

Copying creates a new encrypted version; older retained versions remain under their original encryption. **Do not claim every historical version is customer-managed-KMS encrypted** after migrating only current files. Decide retention, legal holds, rollback needs and any old-version deletion separately. S3 object versions are immutable; re-copying does not rewrite the original retained version. Inventory/archive/version removal needs separate documented authorization. Retained copies increase storage and migration scan charges.

Test cutover by Matter/consumer cohorts, not a blanket in-place rewrite. Capture exact metadata/version links and verify content checksums where available without treating multipart ETags as cryptographic content hashes. Reconcile DB references, resumes/photo paths, archive manifests and export sources. Successful scans, audit events and user actions must match the exact adopted version. Stop on unexpected access denial, tagging failure, skipped scans, encryption mismatch, version races or cost deviation.

## Production observation and recovery

Before broad adoption, route scan-failed/skipped/infected metrics and plan/post-scan-tagging failure events to an operational destination. Proposed minimum: three standard CloudWatch alarms ($0.30/month) and narrowly filtered AWS service EventBridge events to a dedicated SNS topic, alerting only admin@lets-paraconnect.com after approval. Alarm dimensions use the existing plan's exact ID/resource; no document body, personal metadata or bearer link belongs in an alert. These monitoring resources are not deployed or included in minimum staging. Subscription confirmation is a future operational step, not reopening completed application email checks.

Use an operator playbook for investigating key permission errors, service outage, unsupported/password-protected files, exceeded scan limits and tagging failure. Restore scanner permissions or service availability; rescan bounded versions with the approved operator identity; prove a clean tag before reopening access. Never change a bad tag to clean by hand. A database status or an event alone cannot override storage enforcement.

## Rollback

Keep a reviewed snapshot of application release, nonsecret configuration, bucket/key/role policies and protection-plan configuration; secrets stay in secure provider settings. Preserve original object versions and the migration ledger until retention approval. Retain the CMK and scanner grants throughout rollback: disabling/deleting the key makes new files unreadable, and removing scanner grants prevents recovery scans.

First pause migration/new writes or affected document actions and restore the last **KMS-compatible, scan-enforcing** application release. New encrypted files must remain readable to authorized users after code rollback. Do not automatically revert encryption to SSE-S3, delete result tags or weaken quarantine. Restore prior file references only to an existing authorized clean version and recheck participant/assignment/account state. Rollback must not resurrect withdrawn/confidential files or grant a previous assignment access.

Short-lived signed URLs reduce exposure but cannot recall an already downloaded copy; keep S3 denies effective for pending/infected versions. Restore reviewed policies through a controlled change and verify clean read/denied read/scanner canaries again. If compatibility or KMS is unavailable, keep affected files unavailable with the 503 scan/storage error state until recovery. Only delete retained resources/key material after separately approved retention and recovery validation. A production adoption approval does not automatically authorize destroying original versions or encryption keys.
