## Intake and deadline record

Use the existing Admin Inbox ticket. Verify the requester's current account through the normal authenticated channel, or use proportionate verification for someone without an account. Never request a password, full payment details or a Matter document solely to verify identity. An access response must not disclose another person's records.

Record the original receipt time, requester/agent authority, residence and context, requested right, affected categories, applicability decision and supporting source. Identity verification and an appeal must not overwrite the original request date. If coverage is uncertain, assign Samantha an immediate follow-up rather than closing the ticket as exempt.

The existing authenticated triage operation accepts `assignedTo`, `followUpAt` and `nextAction`; its update is audited. Add the fuller deadline record as an internal note. Set `followUpAt` to the earliest next action, acknowledgement or response deadline. A reply can clear a follow-up: inspect the saved ticket afterward and explicitly set its next outstanding deadline. The schema does not independently compute statutory deadlines.

## Preservation before any destructive operation

1. Record Samantha's scope-specific decision, affected IDs, reason, review date and release authority in restricted custody. Keep document bodies and credentials out of public evidence.
2. Identify every affected writer: automation/purge jobs; Admin or account-removal APIs; personal-file replacement and deletion queues; request-time pruning; database TTL; and provider lifecycle/expiry. Record current in-flight task/claim state and the earliest independently scheduled expiry.
3. Stop new affected work and drain existing claims. Maintenance alone does not fence direct requests, an in-flight process, Mongo TTL or S3 lifecycle. Do not declare preservation complete until each relevant writer is stopped, fenced or independently protected under explicit authority.
4. If an expiry cannot be stopped safely, obtain authority for a restricted encrypted preservation copy before expiry. Record exact hashes, version IDs, key custody and restore instructions. A deleted rehearsal backup is not a retained production rollback copy.
5. Compare the protected records and current references. Keep financial, Matter, dispute, policy and audit history required for existing obligations. Account minimization must not cascade into those records. Preserve the separately approved 505 legacy objects.
6. Resume only after a recorded release, fresh reference checks and verified cancellation/revalidation of old claims. There is no universal product legal-hold switch.

## Vendor work and response

Track each affected vendor separately: requested action, minimum identifiers, actual account setting/contract evidence, provider reference, completion result, retained copies and any exception. AWS versioned objects, Atlas snapshots, email archives, Stripe financial records and AI logs have distinct lifecycles. `store:false` in an API request is not a zero-retention attestation. Do not promise erasure from all copies based on a current-object delete or account minimization.

Prepare a response stating completed actions, retained categories/reasons, unresolved scope, review/appeal method and any required complaint route. Verify the intended recipient and actual received response through an authorized delivery check. SMTP acceptance alone does not establish receipt. Link an appeal to the original ticket and record its own receipt/deadline and actual decision. Close only after the saved state, audit, provider outcomes and response evidence agree.

Retain: ticket/reference; original receipt/timezone; verification method/result; request and residence/context; applicability/source/effective date; acknowledgement and response deadlines; any timely extension notice/reason; assigned owner/next action; preservation scope, writer-drain and custody evidence; vendor outcomes; actual decision; received-response evidence; and separately linked appeal.
