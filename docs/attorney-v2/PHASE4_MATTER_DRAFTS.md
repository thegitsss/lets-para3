## Scope and behavior

`#/matters/new` now owns the attorney draft editor. Home, onboarding and Matters creation links open it, and draft rows resume `#/matters/new?draftId=…&step=description`. The three steps cover Matter details, description/tasks and review. Stored fields include title, practice, state, compensation, experience, optional deadline, description paragraphs and ordered task titles. Existing posting choices are retained, and unfamiliar stored values receive explicit options instead of substituted defaults. Blank titles remain blank in the editor; the list's “Untitled Matter” display label is separate. An unfamiliar legacy deadline stays visible as text until corrected.

Incomplete drafts can save. Advancing validates a descriptive title, practice, state and compensation of at least $400 with at most two decimal places. Review additionally requires a description and at least one task, matching the existing publishing page. Optional deadlines must be valid calendar dates. The review estimates the current 22% platform fee using integer cents. Draft saves neither publish a Matter nor charge the attorney.

Typing schedules a save after 1.6 seconds. Each editor permits one write at a time and preserves subsequent typing until its next confirmed save. Save and Return waits for the final edit. Route changes retain unsaved drafts in page memory; closing/reloading warns for unsaved or uncertain writes. Draft text never enters local/session storage, URLs or telemetry. URLs carry only the draft ID or a random creation request ID. Account/session protection clears private editor state. The existing editor clears its draft DOM on pagehide and reloads after a BFCache return.

Failed or ambiguous writes pause autosave and retain text. “Check saved draft” performs a read, using the request ID to resolve an uncertain first creation. It does not retry a mutation. A conflicting version shows each differing field and explicit choices to use the saved draft or keep local edits. Keeping edits adopts saved changes to fields left untouched; tasks are one ordered field. The attorney reviews the result and explicitly saves it. A subsequent concurrent change is rejected again. Missing known draft IDs are never silently recreated.

Deletion requires an explicit confirmation and the reviewed revision. An intervening save prevents stale deletion. An acknowledged deletion clears the editor and offers return/create links. The later [P4-ACT correction](../audits/completion-2026-09-09/matters/action-coverage/README.md) supersedes the earlier404 recovery rule: a missing record cannot prove deletion, so a lost acknowledgement remains unconfirmed and no request is automatically repeated or recreated.

“Continue to publishing” saves the reviewed draft and opens `/create-case.html?draftId=…#review`. This remains a labeled handoff to the existing publishing workflow and is not counted as a rebuilt publishing feature. Routes with a posted `caseId` retain their existing handoff.

## Shared draft contract and compatibility

The authorized draft workflow requires a narrow shared dependency: `CaseDraft`, `/api/case-drafts`, shared draft-only browser modules, the current `create-case.html` adapter, the current dashboard's draft deletion adapter/asset version and the existing draft lifecycle test. All other shared workflows and all paralegal implementation files remain outside this pass. The pre-edit checkpoint records the exact dirty-workspace baseline.

The API retains existing approved attorney/admin guards, authentication, CSRF, owner scoping and list caps. Updated editors also send the expected owner ID, which the server compares to the actual session; an account change after client preflight cannot create a draft under the new account. A mismatch clears the editor and requires signing in again. Responses add `rawTitle`, an opaque `revision` and an optional creation request ID, with no-store caching. PUT and DELETE require the current revision; missing revisions return 428 and stale revisions return 409. An atomic conditional update/delete checks the record's owner, version counter, timestamp and editable-field snapshot, preventing races after the initial read. Unrelated legacy root fields remain intact. An untouched task array retains its original metadata.

POST accepts an optional UUID creation request ID. A partial unique owner/request index prevents duplicate creation. Identical retries return the existing draft; reuse with different creation fields returns 409. Resolving a request is owner-scoped. The client compares returned fields before accepting an apparent replay, so an old create response cannot conceal later edits. Description normalization now preserves paragraph breaks.

The current editor uses the same draft session and recovery controls. It verifies its owning attorney before draft reads/writes, includes revisions, retains failed saves, and waits before Save & Exit. Existing list deletion uses the listed revision and rejects stale requests instead of silently refreshing and deleting newer work. Its compensation review now displays cents. Posted-Matter creation/update rules remain unchanged; draft cleanup after a confirmed post reports any retained draft instead of clearing its identity on failure.

**Release gates:** validate the partial unique index before enabling concurrent creation, deploy the API and both editor adapters together, and require cached/open clients without revision support to refresh. Unversioned PUT/DELETE requests are rejected intentionally. Token-less legacy POST remains compatible and does not gain idempotence. Disabling V2 alone does not revert the shared draft contract; a rollback must retain the matching API and V1 adapter. No index migration, deployment or production inspection was performed here.
