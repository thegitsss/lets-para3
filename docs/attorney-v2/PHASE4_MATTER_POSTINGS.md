# Attorney V2 — Publishing and posted-Matter editing

September 5, 2026. This continuation implements P4-02 and exercises the P4-04 failure/lifecycle scenarios using local synthetic records. P4-02 and P4-04 are accepted locally after the final runs. P4-03 Matter management tools, the rest of the attorney rebuild and production release remain separate work.

## Publishing and recovery

The V2 draft review now leads to an explicit publishing confirmation. It saves the draft first, freezes the reviewed fields during confirmation, and asks for a supported publishing practice area. The current editor uses the same publication controller. Unsupported legacy draft practice labels are visible and never silently mapped to Civil Litigation. The server accepts 1–25 tasks and rejects overflow without truncating the retained draft. Compensation keeps cents, and descriptions keep paragraph breaks.

The new approved-owner API is mounted under `/api/cases/posting` inside the existing case authentication boundary. Publication derives all fields from the owned draft at the reviewed revision; the only field chosen separately is the canonical publishing practice. A MongoDB transaction writes the Case, Job, durable MatterPublication receipt and source-draft publication marker together. The source marker increments its revision and prevents subsequent draft edits. A concurrent source save or deletion causes a conflict instead of publishing stale text.

The receipt has unique owner/request and owner/source-draft indexes. Publishing checks that both unique indexes exist before writing. Identical requests and separate tabs reviewing the same source resolve to the same Case and Job. Reuse of a request for a different review returns a conflict. The receipt remains after source cleanup and posting deletion, so a retained draft cannot republish a removed Matter.

A failed or lost response pauses publishing. “Check publication result” reads the receipt by source draft and does not resubmit. If no publication is found, the editor checks the saved draft and requires another explicit review/confirmation. Publication success is independent of draft cleanup: a failed cleanup displays a success message, the posted Matter link and a cleanup retry. Reloading the original draft URL also resolves the receipt, even after the draft has been deleted. Publishing does not invoke payment operations.

## Posted edits and deletion

V2 `#/matters/new?caseId=…` and current `/create-case.html?caseId=…` use the same posted-Matter editor. The current page keeps its surrounding navigation. Eligible Matter previews provide an Edit posting link. Changes stay in memory and become public only after a before/after review and explicit Save. Only changed fields cross the write boundary.

The owner-only posting read returns editable fields, an opaque revision and authoritative permissions. Revision-checked transactions re-read eligibility and update the Case and linked Job together. Failed Job synchronization rolls back the Case edit. Title, practice, state/location, experience/minimum years, deadline, amount cents and description paragraphs remain synchronized. Unchanged root fields and task metadata are preserved, including legacy fields outside the current schema. Scope changes preserve existing metadata for matching task titles, including duplicate-title ordering. Long posted descriptions retain the Case limit of 100,000 characters; draft normalization never truncates them.

Compensation stays locked after the first application or while invitations are pending. Task scope stays locked after hire. A hiring claim already acquired before the final assignment also blocks editing and deletion, including when it races a transaction. Closed, engaged and read-only Matters cannot be edited here. Deletion is limited to open, never-engaged postings without payment or dispute history; withdrawal history must also be retained. Deletion removes related Jobs and Applications atomically and keeps publication receipts. No unpublish, cancellation or expiry transitions were introduced.

After a conflict, the editor displays local and saved values. The attorney can use the saved posting or keep explicitly edited fields while adopting untouched remote fields, then review and save again. Failed saves preserve text and require a saved-result check before retry. Later typing—including a deliberate undo to the original value—survives acknowledgement recovery. Ineligibility discovered during recovery disables further writes while leaving the unsaved text visible. Deletion uses a separate permanent-deletion confirmation. The later [P4-ACT correction](../audits/completion-2026-09-09/matters/action-coverage/README.md) keeps a lost deletion unconfirmed after404 and clears fields on access denial; a successful write acknowledgement is required to call the posting deleted.

Both editors guard account changes, send the expected owning account on every mutation and use CSRF. Private text stays out of browser storage, URLs and telemetry. V2 route changes retain it in private page memory; account protection clears that state. The current editor clears its DOM and private state on pagehide and reloads after a BFCache return. A session/route refresh during a write marks the interrupted request uncertain, then reads the receipt or saved posting; an abandoned request cannot leave the replacement editor permanently busy. Returning to a tab may detect a conflict before a new write is attempted, and an interrupted confirmation requires review again.

## Compatibility and release dependencies

This bounded dependency changes CaseDraft, the cases/draft routers, a new receipt model and shared current/V2 editor adapters. Existing generic case endpoints remain available for other callers. Historical token-less `POST /api/cases` is not made idempotent by this new receipt flow; old cached clients using it must be refreshed as part of a coordinated release. It is not safe to claim mixed-client publication deduplication across that old endpoint.

These writes require a MongoDB replica set or supported sharded transaction deployment and the verified receipt indexes. There is no fallback to partial Case/Job writes. Production database capability, index installation, backup/restore and rollout were not inspected or performed. The browser harness enables a single-member ephemeral replica set only for the attorney V2 configuration; other test configurations retain the existing standalone default.

Audit and existing participant/discovery notifications run after commit, and only initial publication—not receipt replays—triggers the posting email. These existing best-effort side effects do not have a durable outbox; process failure after database commit can still omit a notification. A notification failure never rolls back or duplicates a committed posting. Operational reconciliation and mixed-version release drills remain release gates.
