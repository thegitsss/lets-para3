# Shared file writes and original upload recovery

Local implementation verified, September 8, 2026. This slice closes the older upload, attachment, review, replacement and scanner write races with Matter decisions. Removal, storage cleanup and the final file presentation remain separate unfinished work; this document does not mark the full attorney experience ready.

## Changes and authority

`services/matterFileWrites.js` checks the actual approved attorney/current assigned paralegal, verified token version, active session, consistent ownership/assignment aliases and current funded-work permissions. A pending invitation or pre-engagement request does not grant these document writes. Completion/hiring claims, revoked access, closed work and account changes stop an earlier request before metadata can be committed.

Existing direct uploads, file attachment, status/revision requests and replacement now write the Case revision and their file metadata in the same transaction. They preserve existing review fields and unknown stored metadata. They do not add an all-files-approved completion policy. A completion/withdrawal or replacement that wins the Case write prevents an earlier request from saving against the new state. Changed security results also serialize with the Case; unchanged scan-result timestamps do not revise the Matter. Scanning an earlier object cannot mark a replacement object clean.

The legacy upload path now retains original request evidence in the existing `MatterFileUpload` collection, including the original owner, exact normalized name/MIME/size/bytes and revision-request context. Every attempt gets its own random storage key and retained identifier. The upload outcome and CaseFile commit together. A retry after either V1 or V2 replacement resolves the original upload and returns its current file identity with `changedSinceUpload`; it cannot create another file simply because the replacement changed `CaseFile.userId`. Different bytes/names cannot reuse that request. A removed recorded upload cannot be recreated by replay. Earlier uploads without byte evidence retain an explicitly unverified origin record when replaced; newer contents are not adopted as proof of the original upload.

A failed storage response or uncertain database commit retains attempt evidence. The request no longer deletes a possibly committed winning object as compensation. Invalid or foreign attachment/replacement keys likewise cannot trigger blind storage deletion. Durable attempt cleanup and reviewed removal are still required in the following slice. Existing known deletion routes remain unfinished until that work lands.

Transactions have no fallback to independent writes. A MongoDB lock timeout marked `TransientTransactionError` before the operation completes can retry at most twice, with fresh account/Matter guards and a short bounded delay. File bytes and notifications remain outside that retry. Changed records, ordinary write conflicts, an attempted commit and unknown outcomes are never automatically replayed. The tests explicitly check that retrying an uncommitted metadata lock sends bytes once, preserves the intended file fields, respects a newly appearing completion claim, and stops after three attempts.

The shared Jest Mongo harness now uses one ephemeral loopback replica member so existing consumer suites exercise real transactions. It preserves the owner-only state file, serial suites, database drop, observed clean process exit and watchdog/temp cleanup. The harness check executes a real commit and rollback. The private candidate keeps its previous shared `tests/helpers/db.js` and `LpcEvent` versions; unrelated newer root edits are not silently included.
