# Attorney application review

September 7, 2026. This is the application-reading portion of P5-01/P5-02. It does not close either checklist item. Application decisions, original submitted-document access, pre-engagement, payment setup and hiring remain open. Release `attorney-v2-application-review-20260907` remains disabled with an empty remote cohort.

## What changed

V2 `/matters/:caseId/applications` now opens a real review screen instead of a generic Matter-workspace handoff. Matter actions and application summaries lead to it. The current dashboard has a **Review applications** Matter action that mounts the same component in the existing account-protected modal. Existing applicant decision controls and their links remain available. The new read component does not call a decision endpoint.

The screen identifies the Matter and displays each applicant's cover letter, recorded submission date, status, star indicator, profile details saved with the application, status history and related invitation responses. Rejected and withdrawn applications remain visible. Unknown status and missing dates stay unknown; accepting an application is not described as confirmed hiring or funding. The view distinguishes the assigned paralegal from an accepted application.

Application-time profile details come from the application record, without replacement by the current profile. Current-profile navigation carries the Matter, applicant, application and return context. Deleted, disabled, missing, unapproved and blocked profiles have no active profile link or current identity. Historical application text remains available to the authorized Matter owner. A recorded résumé or LinkedIn reference is named as an inclusion, with a warning that current-profile documents may have changed. This slice does not claim to retrieve the original submitted document.

Applications are read in pages of at most 25, with explicit Next/Previous controls. Application records are ordered by descending record ID; earlier entries held only on the Matter follow, ordered by recorded application date and applicant ID. A selected applicant can be read directly across page boundaries. Returning to all applications updates the route, so reload retains that selection. Invalid applicant links show an error rather than silently opening other applications. Each navigation reads afresh and replaces the prior page; the screen does not combine stale pages or invent a total count. Refresh returns to the first page of the current selection.

Opening an application is explicitly read-only and does not mark it viewed. Source inspection found no existing viewed-status write in the current drawer. Whether an intentional future preview action should mark viewed remains part of P5-01; a read endpoint must not add that effect incidentally.

## Read authority and compatibility

New GET `/api/cases/:caseId/application-review` requires the expected signed-in account and existing Case access, plus fresh owner/admin checks. It verifies current role, approval, disabled/deleted flags, raw JWT `av`, and active session when supplied. Both owner aliases are supported as BSON ObjectIds or legacy text; contradictory owner references fail closed. The request and response use `private, no-store`. The client also verifies the account before and after the read.

The backend checks the linked Job's attorney and Matter references before reading applications. With no Case-to-Job link it can use a unique reverse Job link. Foreign, ambiguous or contradictory references fail closed. A missing posting yields a visible warning and readable Matter-only history rather than an assertion that no applications exist. Raw reads avoid Mongoose defaults, legacy seeding, record migration, notification sends and status changes.

Application records take precedence over corresponding Matter applicant entries. The response names differences in status, letter, submitted references or stored profile, missing Matter entries and pending synchronization. A withdrawn application's removed Matter entry is expected and is not automatically called an error. Earlier-only Matter entries are labeled explicitly. The service reads terminal application history instead of filtering it out and never repairs disagreements while reading. Malformed legacy entries produce an incomplete notice. Duplicate legacy entries fail closed. A bounded join supports up to 2,000 embedded earlier entries; exceeding that limit produces an explicit support outcome, never a fabricated complete list.

The service rereads ownership, account, source records, current profile visibility and block status during preparation. Changed reads are discarded. DTOs deliberately exclude contact information, private Matter notes, payment fields, raw document/photo keys, synchronization errors, history actor IDs and internal reasons. The browser rejects malformed/foreign payloads, renders all applicant text as text nodes and stores no application content in localStorage or sessionStorage. Failed refreshes clear prior letters and links. Navigation, modal close and account loss cancel the component and discard delayed results.

## Remaining work and findings

P5-01/P5-02 remain unchecked. The new read is not a rebuilt star/reject/hire workflow. The existing star/reject handlers perform an initial active-status read, then call shared update services without a reviewed application revision or a complete assignment/closed-Matter race guard. In particular, the shared status writer can update an accepted application after the handler's earlier eligibility read. Those mutation semantics need a dedicated, tested decision slice before V2 controls can claim safe parity. Existing controls remain an explicitly named compatibility handoff.

Original submitted-document retrieval, intentional viewed effects, complete sorting/filtering, winner/nonwinning lifecycle interpretation, stale eligibility controls, counts and full mirror reconciliation remain open. The normal Application unique index is retained; legacy malformed IDs and cross-type duplicate canonical records need wider reconciliation acceptance. The read endpoint's repeated checks do not replace cross-role realtime convergence or a full snapshot transaction across pages. Existing invitation sending/revocation, pre-engagement review, pending hire and funding remain the subsequent Phase 5 work.
