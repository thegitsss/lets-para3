This is a bounded part of P8-03, under the controlling [LPC Product North Star](../LPC_PRODUCT_NORTH_STAR.md) and [attorney editorial standard](EDITORIAL_STANDARD.md). ## Behavior

Matter Financials shows the original Matter amount, attorney fee, exact payment total, currency and recorded funding evidence. It uses the same verified financial-row adapter as the financial history. A Case flag alone cannot certify funding; original funding is distinguished from refunds, payouts and remaining Matter funds. Failed reads remove action controls instead of presenting an empty or funded state.

Review payment details prepares or retrieves one payment without confirming a charge. The payment form names the Matter, amount, fee and assigned paralegal. A separate Fund Matter action confirms through Stripe. Check Stripe payment verifies provider evidence and records the current result. Account changes clear confidential state and destroy the form; pending work survives Matter-tab navigation only in page memory. Client secrets are not stored in browser storage or audit records. Redirect parameters are removed when the module loads, and a redirect's claimed success is never trusted as payment evidence.

The existing `/intent`, `/start-escrow`, `/confirm`, `/reconcile` and budget routes share the same fresh-account and Matter checks. Administrator checks retain their actual actor role, status response fields and audit identity. The confirm endpoint retains its 402 response for an incomplete payment. Eligible posted amount changes link to the actual V2 editor. The legacy budget endpoint now saves the exact-cent Case/Job update and audit in one transaction. Financial, engagement and retained-history locks apply before changes; arbitrary currency changes or silently rounded decimal inputs are rejected.

Pending escrow reads formerly called `ensureCheckoutUrl`, which could create a provider checkout session and save the Case during a GET. They now return the Matter financial-review destination without provider writes. Existing checkout references and unresolved funding keys block a competing payment; their complete historical recovery and active/pending-list treatment remain in P8-09.

## Financial safeguards

- Preparation claims the existing durable funding key and records the reviewed request before provider creation. Exact replay never repeats creation, including after the provider's idempotency window. Unknown results stay unresolved; the browser checks their outcome rather than resending a charge.
- A known returned PaymentIntent ID is retained before another account/Matter check. A changed customer, fee, assignment or Matter record prevents exposure of the old form. Reusing an existing intent verifies its amount, currency, owner metadata, customer, transfer group and mode.
- A canceled intent can be replaced only after provider confirmation of zero received funds and no charge evidence. Changing the fingerprint, amount or UI surface cannot rotate an unresolved shared funding key.
- Successful checks require matching PaymentIntent, captured charge and balance-transaction evidence, with exact amounts, currency, mode and relationship IDs. Duplicate Case or operation references remain unverified. Case, funding operation and check audit commit together; audit failure rolls them back.
- A historical payment check preserves completed, closed, withdrawn, disputed, released and remaining-balance state. The ordinary assigned open Matter becomes active only after successful verification. Processing is never treated as funded.
- Posting edits and budget changes respect payment/session/request history and competing completion/withdrawal/hiring claims. The original Matter amount is not relabeled as currently available cash.

Stripe documents separate creation from confirmation and describes the eight-digit minor-unit amount limit in [Create a PaymentIntent](https://docs.stripe.com/api/payment_intents/create). The implementation follows its [confirmation/redirect contract](https://docs.stripe.com/js/payment_intents/confirm_payment?type=card) and verifies the relationships described by the [Charge](https://docs.stripe.com/api/charges/object) and [Balance Transaction](https://docs.stripe.com/api/balance_transactions/object) records. No real Stripe operation was performed during this work.
