## Behavior and authority

The baseline reproduced both directions of the existing application withdrawal/hire race: withdrawal could proceed while a hire was charging, and an earlier active canonical Application could authorize a hire after withdrawal had removed its Matter entry. The paralegal revoke route now atomically removes its Matter entry, adds a private withdrawal interlock and advances the retained Matter revision before attempting the canonical status update. A hiring claim wins that same Matter write or loses before a charge. A canonical write failure retains an explicit reconciliation marker; it cannot revive eligibility. A later rejected/accepted status is never overwritten by the earlier withdrawal attempt.

`Case.withdrawnApplicantIds` is an optional, unselected array of ObjectIds. It distinguishes a withdrawal in progress from a legitimate earlier canonical-only application. Earlier canonical-only applications retain their current-client hiring/pre-engagement permissions. The interlock is not returned in ordinary model reads or Matter DTOs; no bulk record migration or transaction fallback is introduced. Explicit later reapplication can establish a new active mirror. Normal revoked Application status remains authoritative after synchronization.

Accepted-invitation revocation uses the same claim/version boundary. Acceptance still synchronizing cannot be reversed by an overlapping application or invitation withdrawal. Revocation still synchronizing cannot be resent through either attorney client. Stable repeated acceptance does not replay canonical writes. Existing pending/declined/expired outcomes, amount locks, role restrictions, events and notification contracts remain. The legacy invite route also preserves its existing authorized owner-alias repair using the original aliases in the atomic write filter; the previous invitation slice had unintentionally compared the repaired in-memory aliases to the older stored aliases.

The current Matter deletion route now atomically checks the owner references and its never-engaged state, including pending/unknown funding claims and request keys. It cannot delete a Matter while a hire is charging. Deletion that wins first prevents a subsequent hire from acquiring it. Existing reviewed posting deletion remains separately covered by `matterPostings.test.js`.

Current hiring reads earlier text/BSON canonical and mirror references consistently. Its accepted/nonwinning status updates and Job count use the same reference compatibility, without reactivating withdrawn applications. A new application arriving after charging begins makes strict finalization stop with the payment reference retained. After a fresh review, the attorney can explicitly finish the verified earlier hire without another card charge; the new nonwinning application remains in rejected history.
