# Reviewed document removal and retained storage

This work is part of preparation for the owner's full Attorney V2 review. It does not finish Phase 7, release Attorney V2, retire V1 or authorize provider operations against real records.

## Result and authority

The Files view names the document and version before offering removal. It explains the effect on Files and retained correspondence/history, provides an explicit confirmation, keeps an uncertain request in tab memory, checks the exact recorded result after a dropped response, and requires another explicit confirmation for a retry of the same unchanged request. Stop waiting cancels the browser wait; it does not claim to cancel a committed server operation. Account changes erase the private state.

`MatterFileRemoval` stores the original raw CaseFile snapshot, matching removed Case.files mirrors, original owner/request/review, retirement references and removal time. The response uses a separate explicit DTO. Known sensitive file fields remain encrypted in the private retained snapshot. An HMAC review digest covers the raw document, Matter write boundary and mirrors; metadata or preview changes invalidate a displayed review. Unique owner/request and Matter/file indexes bind replays and prevent duplicate removal outcomes.

Removal, original upload receipt preservation, Case revision, matching mirror changes, the existing audit activity and storage-retirement records commit together. Earlier routes retain their audit action names; private raw file keys are kept out of the new audit metadata. There is no fallback to separate destructive writes. Lost commit acknowledgements are checked against the exact retained result. Fresh approved account, verified token authVersion/session, consistent Matter owner/assignment aliases, funded active work and completion/hiring claims are checked. Closed/purged reviews follow the existing individual-file access policy. The two older deletion routes now use this removal service; the by-key route's previous paralegal deletion permission was inconsistent with the explicit attorney-only deletion route and both product interfaces, and is now attorney-only.

## Storage and other writers

The scoped `MatterStorageRetirement` queue is separate from personal-file deletion. Its retired-key records have no TTL. Every supported current document upload/attach/replacement and file-message write checks the retired key inside its Case transaction, preventing a delayed metadata write from reattaching a retired object.

The worker checks current documents, previews, earlier versions, Case.files, current/earlier message attachment aliases, retained removal history and reference fields in unknown retained containers. Ordinary message text cannot manufacture attachment access by naming a retired key. Soft-deleted messages conservatively hold their copies. Incomplete, undecryptable or excessively deep reference inventories do not authorize deletion. Unsafe/foreign/unrecognized keys and a changed storage bucket retain private evidence for review without a provider delete. New signed reads of retired objects require a retained reference visible to the current assignment; exact message attachment reads keep their existing authorization.

Upload attempts record their own provider settlement. Expired claims are fenced before loser cleanup; a recorded winning attempt is excluded. A late acknowledgement updates only its original attempt. An unknown PUT outcome remains subject to recurring cleanup even after a successful delete response, because that response cannot prove a pending upload will never arrive. An exact recorded acknowledged attempt can finish cleanup. Retained reference holds are revisited; claim tokens stop stale workers overwriting a newer worker's result. The bounded worker is wired into light/full automation cycles and respects their existing maintenance stop.

Legacy replacement now clears the old preview metadata and records its retirement atomically. V2 preview retirement and older stored retirement evidence use the same queue. Earlier document and removed-mirror versions remain available to archive preparation, with existing completeness limits and key validation; private removal evidence and an unreferenced removed current copy are excluded from the exported archive.

## Remaining file work and release evidence

The API-only legacy `/uploads/presign` path has no frontend caller in the current source inventory. It still needs durable orphan-upload accounting, fresh write authority and an overwrite-resistant signed-PUT contract before full file convergence is accepted. Its current issuance expires after 60 seconds; other signed reads have separate TTLs. Existing signed URLs may remain usable until their actual provider expiry.

AWS documents that a same-key presigned upload can replace an existing object, and that an `If-None-Match: *` conditional write prevents overwriting an existing current object. See [presigned URL behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) and [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html). This source review informs the next bounded compatibility change; no real bucket policy, CORS setting or provider operation has been changed. Previously issued URLs and provider/versioning behavior require separate operational evidence.

V1 displayed-content binding, full earlier whole-file list/download compatibility, removed-history selection while active, whole-file convergence, retention purge races and full final-candidate acceptance remain open. `purgeExpiredCases` still needs a disposition for per-object provider deletion errors and its final Matter guard. Real provider timing, versioned bucket lifecycle, worker deployment and multi-instance behavior are release evidence; local storage substitutes cannot prove them.
