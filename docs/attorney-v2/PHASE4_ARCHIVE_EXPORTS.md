# Attorney Matter archive exports

Recorded September 6, 2026. This is the archive-download continuation of P4-03, with bounded dependencies on P6-03 and the later completion/retention workflows. It is not closure of Phase 4 or the attorney rebuild. Apply the [attorney editorial standard](EDITORIAL_STANDARD.md).

## Result

Both attorney dashboards now offer **Review archive download**. The review names the Matter, counts its retained messages and documents, identifies included prior file versions and confidentiality documents, and shows the retention deadline before an explicit **Download archive** action. Unavailable, expired, purged, unreadable and oversized archives have distinct explanations. A failed refresh clears the previous review. Cancellation, navigation and account changes discard pending downloads. The confirmation says the browser download was requested; it does not claim a file was saved to disk.

The current dashboard's completed-Matter history uses the same review, with lazy, idempotent dialog setup. Existing dormant bulk-action code now uses a review sequence with an explicit download for each Matter; no new bulk controls are exposed. The sequence is tested as a component because the current HTML has no bulk selection controls. The V2 route is `#/matters/:caseId/export`; Matter navigation remains selected there.

## Contents and retention

Every on-demand download builds a fresh ZIP containing `Case_Summary.pdf`, `Archive_contents.json` and retained documents. It never serves a previously cached archive. Contents are collected from current CaseFile records, recorded prior versions, both pre-engagement confidentiality documents, legacy Case file references and retained message attachments. BSON and historical string references remain readable. Repeated storage keys are included once; ZIP names cannot escape their directory or overwrite another name through case or sanitization collisions.

The PDF preserves message text, line breaks, literal angle-bracket text, recorded transcripts and reply context. It does not guess which separately uploaded document belongs to a message. Short message entries stay with their sender and date across page breaks. Unknown dates, amounts and task completion are stated as unavailable or unrecorded. The manifest lists actual staged byte counts and ZIP paths without exposing storage keys.

Deleted messages, private Matter notes, file revision notes and platform financial receipts are excluded. A legal document called **Receipt of service.pdf** remains included; exclusion is limited to reserved platform receipt/archive storage keys. File security checks bind to the exact storage version when available, with conditional reads, matching metadata, bounded byte counts and a second scan check before preparation completes. Missing or changing bytes fail the whole export instead of silently omitting documents.

Purged or expired archives are refused before storage access. The recorded `purgeScheduledFor` takes precedence. Completed/closed historical Matters with a completion date use the existing six-month policy when the explicit deadline is missing. An unconfirmed final retention date prevents download. A manually archived posting without a scheduled deletion date says so. Ownership, account/session access, retention and source revisions are checked again during preparation.

## Preparation and compatibility

On-demand exports stage files in a unique private temporary directory, prepare the entire ZIP before response headers, send a known content length and clean up after success, error or disconnect. They perform no archive-storage upload, overwrite or delete. Concurrent requests cannot delete or replace one another's ZIP. The shared completion generator uses the same validated builder and distinct archive object keys; failed uploads are aborted and local files are removed. Existing completion and payout authority remains in place.

`GET /api/cases/:caseId/archive/export` returns the account-bound review. The existing `GET /api/cases/:caseId/archive/download` remains available to the owning attorney and currently authorized administrators, with fresh preparation even for legacy direct links. A reviewed revision is checked when supplied. No publication, archive-status, financial or receipt mutation is added by these read endpoints; normal authentication session bookkeeping remains possible.

Final access review found that the archive and existing attorney receipt guards read `authVersion` from the raw JWT, while the verified token contract carries the version in `av`. Both guards now use that contract. Renewed sign-ins after password/security changes remain valid, and a later version change during preparation prevents delivery. The two receipt paths were added to this change only after matching their initial manifest hashes. The final targeted archive/receipt run passed 78/78; the overall latest backend/model total is 190.

Preparation refuses more than 10,000 retained messages, 2,000 CaseFile records, 4,000 distinct documents, 250 MiB of source documents or 16 MiB of serialized source text. A 120-second signal bounds storage and ZIP operations and is checked between preparation stages. The browser also refuses ZIPs over 270 MiB, wrong content types and missing initial/final ZIP records. These are preparation safeguards, not a production load-capacity claim.

The installed Archiver 8 API requires its `ZipArchive` constructor. Its minimatch 10 dependency also required brace-expansion 5, while the repository's global override forced version 2. A scoped `minimatch@>=10` override restores compatibility without replacing the older dependency branch. Actual ZIP creation and CRC/entry checks exercise the installed library. The lockfile adds the required brace-expansion/balanced-match pairs for readdir-glob and nodemon; existing root versions stay unchanged.
