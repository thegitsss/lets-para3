# Attorney Matter file uploads

This slice implements selecting, confirming, sending and recovering an attorney document upload. It belongs to P7-03/P7-04; deletion, replacement, full document history and storage reconciliation remain separate work. The full attorney experience is not ready for owner review yet.

## Authority and behavior

The new GET `/api/uploads/case/:caseId/upload-review` and POST `/api/uploads/case/:caseId/reviewed-upload` use the fresh attorney account/session and raw Matter authority shared by document review. Uploads require the existing active, assigned, funded workspace conditions and reject archived/read-only/released/revoked or concurrently claimed Matters. The POST binds the displayed Matter authority; both reads and confirmed writes recheck account access. The original upload endpoint and paralegal revision-submission contract remain available.

Selection accepts the existing document types and 20 MB maximum. The server verifies file signatures and MIME/extension agreement. The confirmation names the chosen document and explains sharing with the assigned paralegal after security checks. Progress is indeterminate because Fetch does not report transferred byte counts here. The attorney can stop waiting; cancellation says that the server might still save the document. A three-minute client limit likewise preserves uncertainty.

A new `MatterFileUpload` record binds the owner, Matter and request ID to the normalized filename, MIME and exact byte fingerprint. Its required unique index is checked before offering uploads. Each explicitly claimed attempt receives a distinct private object key. A 90-second lease and conditional claim token prevent overlapping attempts from both recording. Up to five attempts are retained; no background retry sends document contents. The final transaction writes the Matter guard, normal encrypted `CaseFile`, and recorded upload outcome together. A fresh account read precedes commit. This route does not fall back to nontransactional persistence.

The client retains its selected `File` and request ID only in tab memory, including internal route changes. A dropped response can be checked using the exact request ID. Confirmed uploads return the recorded file; an upload whose file has since been removed is reported as recorded/unavailable and is never recreated by replay. A changed payload using the same ID is rejected. A failed or unconfirmed transfer can be retried only through an explicit action after its status is checked. Account protection clears the selection.

No compensation blindly deletes an object after an uncertain database commit. Attempt identifiers are retained for reconciliation. **Durable physical cleanup of unsuccessful attempt objects remains open** and must be finished with the Matter document deletion/storage work; the existing personal-storage deletion queue does not accept Matter keys. There is no claim that local upload tests certify deployed storage lifecycle or malware scanning.
